# Qwen3-8B DSpark drafters: dense and MoE, managed-local

Two single-node recipes train DSpark drafters for `Qwen/Qwen3-8B` (36 layers,
hidden 4096) on one 8-GPU node and differ only in the draft config:

| Recipe | Draft config | Drafter |
| --- | --- | --- |
| `examples/configs/online/disaggregated/managed-local/qwen3-8b-dspark-noconf-b16-perfectblend-2server-dp6-disaggregated.yaml` | `configs/qwen3-8b-dspark-noconf-b16.json` | dense, 5 layers, FFN 12288, ~1.05B parameters |
| `examples/configs/online/disaggregated/managed-local/qwen3-8b-dspark-moe-noconf-b16-perfectblend-2server-dp6-disaggregated.yaml` | `configs/qwen3-8b-dspark-moe-noconf-b16.json` | MoE, 5 layers, 8 experts x 4096 top-1 + shared 2048, ~2.4B total / ~0.7B active |

Both use the skeleton of `configs/qwen3-8b-dspark.json` with two changes taken
from the published Qwen3-8B dense DSpark run on this corpus
([jiapingW/Qwen3-8b-dspark-SpecForge](https://huggingface.co/jiapingW/Qwen3-8b-dspark-SpecForge),
step 39000: gsm8k accept length 9.72 at D16/V16): **block size 16** and **no
confidence head** (`enable_confidence_head: false`, `confidence_head_alpha: 0`,
`training.dspark_confidence_head_alpha: 0`). The rest is unchanged: GQA 32/8
heads of dim 128, target feature layers 1/9/17/25/33, vanilla Markov head
(rank 256), `mask_token_id` 151669, bidirectional attention inside the draft
block.

That run's `is_causal`, `dspark_flatten_projection`, `dspark_cache_projection`
and `ddp_bucket_cap_mb` belong to the unmerged PR #942 and are not used:
`is_causal` would switch the draft block to causal attention (a different
drafter variant that also needs serving support), the two projection knobs
only speed up the vocabulary projection, and the DDP bucket size only tunes
communication. Everything else in that recipe is reproduced below.

## The MoE drafter

`configs/qwen3-8b-dspark-moe-noconf-b16.json` is the Qwen3.8-27B MoE drafter structure
(`qwen3_5_moe` preset: softmax top-k routing, one sigmoid-gated SwiGLU shared
expert, auxiliary load-balancing loss, Qwen checkpoint naming; Kan's router
settings `moe_router_center: sample`, momentum 0.99, aux coefficient 0.001,
`grouped_mm` dispatch) at the Qwen3-8B width:

| | Qwen3.8-27B MoE drafter (`qwen3.8-27b-dspark-moe-v2.json`) | Qwen3-8B MoE drafter |
| --- | --- | --- |
| draft hidden (= target hidden) | 5120 | 4096 |
| routed experts x width | 512 x 512 | 8 x 4096 |
| experts per token | 10 | 1 |
| `norm_topk_prob` | true | **false** |
| shared expert | 1 x 2048, sigmoid gate | 1 x 2048, sigmoid gate |
| active FFN width / dense FFN width | 7168 / 17408 (41%) | 6144 / 12288 (50%) |
| routed capacity / dense FFN width | 15x | 2.7x |
| routed parameters (5 layers) | 20.1B | 2.0B |

**Top-1 needs `norm_topk_prob: false`.** The preset renormalises the selected
top-k probabilities to sum to one. With a single expert that weight is
identically 1, the expert output no longer depends on the router logits and the
router receives no gradient from the task loss (only the balance loss moves it,
towards a uniform but meaningless assignment). `MoEConfig` now rejects
`num_experts_per_tok: 1` with renormalisation on; the config keeps the softmax
probability as the combine weight (Switch-Transformer style), which the tests in
`tests/test_modeling/test_moe_qwen3_8b.py` pin down (weight in (0, 1), gate
gradient from the task loss alone, DSpark forward/backward, checkpoint naming,
meta-device parameter counts).

Exports write the recipe to `config.json` (`n_routed_experts` 8,
`num_experts_per_tok` 1, `moe_intermediate_size` 4096, `norm_topk_prob` false,
`topk_method` greedy), so a Qwen-MoE style loader (SGLang `FusedMoE` with
`renormalize=False`) serves it like the Qwen3.8-27B MoE drafter.

## Corpus

Open Perfect Blend regenerated by Qwen3-8B at temperature 0 with thinking off:
`yaro1214/open_data/perfectblend_train_regen_temperature0_no_think.jsonl`
(6.3 GB, 1,420,909 rows, SpecForge `{id, conversations, status}` format, no
`<think>` markers, 96% single-turn). It is used as published; the recipes render
it with `chat_template: qwen3-instruct` (the empty think block of a non-thinking
turn carries no loss) at `max_length: 8192`.

```bash
hf download yaro1214/open_data perfectblend_train_regen_temperature0_no_think.jsonl \
  --repo-type dataset --local-dir ./cache/dataset
```

## Layout and schedule

Managed-local on one node: two TP1 bf16 capture servers (`--spec-capture-method
dspark`, aux layers 1/9/17/25/33) on GPUs 0-1, ports 30000-30001; six DDP
trainer ranks (`fsdp_sharding: NO_SHARD`) on GPUs 2-7. `batch_size 2 x
accumulation_steps 11 x 6 ranks` is a global batch of 132 (the published run
used 128 on 32 ranks), so one epoch is 10,765 optimizer steps and the planned
six epochs are 64,590. AdamW, lr 6e-4 cosine with 4% warmup, grad clip 1.0,
512 anchors, `loss_decay_gamma 7.0`, DSpark loss `0.1 CE + 0.9 L1`, Liger
kernels, one retained checkpoint every 3,000 steps.

The capture servers need the SGLang spec-capture patch
(`scripts/apply_sglang_spec_capture_patch.sh`); `sglang_context_length: 8208`
is `max_length + block_size` headroom for the capture requests.

## Smoke and launch

Three optimizer steps on a 2,000-row slice, all services managed by the
supervisor. DSpark's loss-mask filter applies `data.max_prompts` only after the
whole file is tokenized, so slice the file for a fast smoke; set
`model.target_model_path` to a local directory when the Hugging Face cache is
read-only.

```bash
head -n 2000 ./cache/dataset/perfectblend_train_regen_temperature0_no_think.jsonl \
  > ./cache/dataset/perfectblend_smoke_2000.jsonl
specforge train \
  -c examples/configs/online/disaggregated/managed-local/qwen3-8b-dspark-moe-noconf-b16-perfectblend-2server-dp6-disaggregated.yaml \
  data.train_data_path=./cache/dataset/perfectblend_smoke_2000.jsonl data.cache_dir=./cache/qwen3-8b-smoke-moe \
  training.max_steps=3 training.save_interval=3 training.log_interval=1 tracking.report_to=none \
  run_id=qwen3-8b-dspark-moe-smoke output_dir=outputs/qwen3-8b-dspark-moe-smoke \
  deployment.disaggregated.control_dir=outputs/qwen3-8b-dspark-moe-smoke/control
```

The same overrides with the dense recipe smoke the dense arm. Drop the
overrides for the one-epoch run; `specforge export` materialises the
`<run_id>-latest` checkpoint as a servable directory.

## Smoke results (2026-10-15, one 8x H200 node, SGLang 0.5.18 with the capture patch)

Three optimizer steps on the 2,000-row slice with the overrides above
(`max_steps 3` leaves no warmup, so the learning rate starts at its peak and
the step-2 loss spike is expected); both arms exit 0, save `*-step3` and
export to HF format.

| Arm | step 1 loss (CE / L1) | step 2 | step 3 | trainer peak memory / rank | optimizer step (steps 2-3) | export |
| --- | --- | --- | --- | --- | --- | --- |
| dense, block 16, no confidence head | acc 0.000 | acc 0.037 | acc 0.014 | ~40 GB | ~5 s | 2.25 GB, `config.json` block 16 |
| MoE 8 x 4096 top-1, block 16, no confidence head | 3.23 (14.27 / 2.00) | 7.10 (53.5 / 1.93) | 3.34 (15.4 / 1.97) | 78 GB | 6.5-7.9 s | 5.02 GB, 8 experts, top-1, `norm_topk_prob` false |

MoE routing on the MoE arm: `moe/aux_loss` 0.0010 -> 0.0015,
`moe/experts_unused_frac` 0.000 -> 0.025, `moe/load_frac_max` 0.29 -> 0.43
over the three steps (sample router centering active).

One finding from these smokes: with `fsdp_sharding: NO_SHARD` the backend
wraps the training model in DDP, which does not forward attribute access the
way FSDP does, so the MoE helpers that read `wrapper.draft_model` found
nothing and NO_SHARD MoE runs trained without the balance loss and logged no
`moe/*` metrics. `_wrapped_draft_model` in
`specforge/training/strategies/base.py` now resolves the draft through
`.module`; `tests/test_modeling/test_moe_qwen3_8b.py` covers it.

Throughput note: at global batch 132 the MoE arm's steady optimizer step is
about 7 s on six H200 ranks, i.e. roughly 21 hours per epoch of the full
corpus (10,765 steps); the dense arm is faster. The capture servers were not
the bottleneck after warm-up (`perf/data_wait_time_s` < 1 s).
